# Days 18–21 — The usable document Q&A workspace

The local browser app now connects uploads, durable ingestion, questions, streamed
answers, private history, and source inspection. The interface uses a light paper
and graphite palette, pencil-like marks, hover feedback, subtle transitions, and
reduced-motion support.

Issues: [Day 18](https://github.com/Justin-Mendoza/Afterclass/issues/16),
[Day 19](https://github.com/Justin-Mendoza/Afterclass/issues/20),
[Day 20](https://github.com/Justin-Mendoza/Afterclass/issues/19),
[Day 21](https://github.com/Justin-Mendoza/Afterclass/issues/25).
[Design decisions and approved plan](days-18-21-decisions.md).

```text
Browser → Next.js forwarding route → FastAPI authorization
  ├─ Upload → saved receipt/job → ingestion worker → searchable chunks
  └─ Question → authorized retrieval → Cohere stream → provisional text
       → citation checks → saved private result → checked citations + completion

Citation click → saved-answer access check → supporting snapshot + file metadata
Original download → current document access check → attachment
```

## Run the app

Use the existing `.env` setup with a valid `COHERE_API_KEY`. Compose accepts the
legacy `COHERE_TRIAL_KEY` when the canonical key is unset. Provider keys remain on
the backend; the browser receives only the selected simulated demo identity.
Uploads and questions in the normal app can incur Embed, Rerank, and Chat charges.

```sh
make stack-up
```

For the already-initialized project, open <http://localhost:3000>. When ports are
occupied, use explicit overrides; for example:

```sh
export FRONTEND_PORT=3005 API_PORT=8005 POSTGRES_PORT=55432
make stack-up
```

The frontend forwards requests through its own `/api/v1/...` URLs to
`API_INTERNAL_URL` (Compose: `http://api:8000`; host development defaults to
`http://127.0.0.1:8000`). For separate host development, set `API_INTERNAL_URL` on
the frontend process to the actual API address. This avoids browser cross-origin
configuration and keeps all authorization/search rules in FastAPI.

Existing volumes retain documents, tokenizer assets, indexes, and database state.
No new database migration is required beyond Day 18. If preparing a fresh stack,
apply the existing migrations and seed the demo identities:

```sh
docker compose run --rm --no-deps -v "$PWD/backend:/work:ro" -w /work api alembic --config alembic.ini upgrade head
docker compose exec api python -m hybrid_rag_search.seed
docker compose exec api python -m hybrid_rag_search.tokenizer_setup
```

The explicit tokenizer setup may download the pinned tokenizer asset. The answer
path never downloads it implicitly. A fresh search index also needs the existing
two-phase index setup; run this only when initializing an empty stack, not to
replace an existing working index:

```sh
docker compose exec api python -m hybrid_rag_search.index_rebuild start first-demo
docker compose exec api python -m hybrid_rag_search.index_rebuild promote hybrid-rag-chunks-v3-first-demo
```

If rebuilding an existing corpus, ingestion must finish before promotion; existing
rebuild commands can enqueue paid embedding work. Keep using the existing read
alias until the rebuild is ready.

## Try the workflow

1. Select a demo identity and workspace. These are simulated identities, not real
   login accounts. User switching changes permitted collections and clears old
   answer/source content and in-flight requests.
2. Choose a collection, open Documents, and upload a PDF, plain-text, Markdown, or
   HTML file. The server enforces the configured upload limit (default 20 MiB).
   Watch upload progress and then the saved ingestion job until it succeeds.
3. Open Ask a question and ask about the selected collection. “All accessible
   collections” is an explicit alternative. Questions are independent; saved
   history is not sent as conversational context.
4. Read the live draft marked unverified. It is replaced with the authoritative
   result after validation. Final outcomes distinguish answered, partial,
   insufficient evidence, and failure. Source checks establish reference validity,
   not semantic truth of every claim.
5. Click an inline citation or source chip. The source panel shows the exact chunk
   supplied to the model, with page/heading/block locations where available. It
   rechecks access through the saved-answer API and obtains filename metadata
   through the document API. Original files download as attachments; uploaded HTML
   and provider text are never executed or rendered as raw HTML.
6. Stop an active answer, or use manual Retry after failure/interruption. Recent
   questions load author-private saved results. Direct answer/source links go
   through the same API checks; another identity cannot read the author's history.
7. Owners/admins can create collections. Authorized collection managers can edit
   them and change grants. Upload/manage capabilities come from the backend;
   hiding a button is not the authorization boundary.

## Stream contract

`POST /v1/workspaces/{workspace_id}/answers/stream`, using `X-Demo-User-ID`:

```json
{"question":"How long do upload receipts last?","collection_id":null}
```

`collection_id` is optional. Unknown request fields and blank/overlong questions
are rejected. Authorization and unsupported `Last-Event-ID` resume requests are
checked before the response starts. Responses use `text/event-stream`, no-store
caching, monotonic request-local event IDs, and JSON data. Progress/content events
can repeat; success ends with citations and exactly one completion; failure ends
with exactly one error. Keepalive comments are not content or timing events.

| Event | JSON payload |
| --- | --- |
| `progress` | `type`, `stage`: `retrieving`, `generating`, `validating`, or `saving` |
| `content` | `type`, `text`: a provisional text increment, never a final answer |
| `citations` | `type`, `citations`: checked answer offsets/text and source IDs |
| `complete` | `type`, `answer_id`, `result`: the authoritative `AnswerResult` |
| `error` | `type`, `code`, safe `message`, nullable `answer_id` |

The result retains Day 18's outcome/text/citations/evidence/model/usage/error and
configuration fields. Configuration includes `timings.first_content_ms`,
`timings.total_ms`, and `timings.generation_ms` where available. First content is
measured to the first user-visible draft increment after the internal status
prefix, not the first progress message. Total time measures processing through
final validation, before the history commit; generation time is the provider's
reported adapter latency. These are not billing measurements.

The client parses arbitrary UTF-8/network chunk boundaries and checks event order.
It replaces the draft with final text rather than appending a second answer.
Citation offsets count Unicode characters on the backend; the frontend explicitly
converts from JavaScript UTF-16 units when rendering references.

## Cancellation, failure, and persistence

- Each request owns its retrieval, SDK stream, bounded event queue, and cleanup.
  Stop/disconnect cancels active work where supported and closes resources.
  Closing a connection does not guarantee the provider stops billing immediately.
- Unfinished cancellation drafts are not saved. Completed validated answers,
  partial answers, and insufficient-evidence outcomes are saved. Failure records
  contain safe error codes without rejected answer prose or evidence.
- Once a result commits, a later disconnect cannot remove it. On an interrupted
  connection, check history before retrying: completion may have been saved just
  before the connection was lost.
- A storage failure produces an explicit error without claiming the result was
  saved. Invalid citations clear the live draft and report a safe failure.
- No automatic reconnect, replay, or model retry. Manual retry makes a new request
  and may incur new charges. SSE event IDs only establish order within one request.
- The answer-processing deadline is configurable with
  `ANSWER_REQUEST_TIMEOUT_SECONDS` (default 90 seconds); provider timeouts remain
  independently configured (Chat defaults to 30 seconds). The frontend also aborts
  a stalled connection after 95 seconds. Failures can happen after headers start,
  so clients must read the terminal event, not just HTTP status 200.
- History/source access follows the existing request-time authorization model.
  Revocation/deletion withholds saved content on subsequent reads; it cannot erase
  a draft already delivered to a client.

## Verification and limits

Checks completed for this implementation:

- 882 default backend tests, 100% line coverage; Ruff formatting/lint and strict mypy.
- 13 real PostgreSQL/OpenSearch integration tests, including migrations and the
  upload → ingestion → retrieval → streamed result → history → source-deletion flow.
- 27 frontend tests for HTTP forwarding/abort, SSE framing/Unicode, uploads, Stop,
  manual Retry, final/failed/interrupted states, identity changes, and source links.
- Browser inspection and automation at desktop and mobile sizes: real management
  and streaming APIs, durable upload job completion, citation inspection/direct
  link reload, identity switching, no horizontal overflow, and reduced motion.
- Text contrast review, keyboard-focus improvements, and larger coarse-pointer
  targets. This is not a claim of a complete screen-reader or formal WCAG audit.
- Frontend formatting, lint, typecheck, and production build; Compose validation.

All model work during verification used explicit offline fixtures. The integration
and browser runs used disposable databases and isolated search indexes; persisted
user data was preserved. Live Cohere streaming/billing behavior was not tested.

The old host `.venv` interpreter is broken. Backend checks used an isolated Python
3.12 environment at `/private/tmp/afterclass-check`, installed from `backend[dev]`;
frontend checks used the existing Node 22 environment. The standard commands are
`make check` and `make db-test` once the host environment is repaired. Direct
commands used for backend verification were:

```sh
/private/tmp/afterclass-check/bin/ruff check backend
/private/tmp/afterclass-check/bin/ruff format --check backend
/private/tmp/afterclass-check/bin/mypy backend/src
/private/tmp/afterclass-check/bin/pytest backend
DATABASE_URL=postgresql://hybrid_rag:local-development-only@127.0.0.1:55432/hybrid_rag /private/tmp/afterclass-check/bin/pytest backend -m integration --no-cov
```

Real student accounts, public hosting, multi-turn context, rebranding, study guides,
and Day 22 search diagnostics remain deferred. No new framework, service, answer
queue, replay store, or always-on recovery process was added.
